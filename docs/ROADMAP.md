# pAstroCORE Roadmap

Bringing the application onto MSB 1.0.0, and putting the parts of it that were written under
time pressure into the shape the framework now makes possible.

**The first rule, because everything else depends on it: the calculations are correct and must
stay correct.** They are the product. Nothing in this plan is worth a wrong schedule, and the
first stage exists only to make that verifiable rather than hoped for.

## The scope rule

The same rule that got MSB to 1.0, for the same reason:

| Situation | What happens |
| --- | --- |
| A new idea arrives | It goes in the table and waits its turn |
| A bug is found | Fixed if it produces a wrong result or breaks a user's project file; otherwise it queues |
| An item turns out bigger than its row | Cut it down or move it out. The stage does not grow |
| An item could be "improved further" | It is done when its exit criterion is met |

## What the codebase actually is

Measured on 2026-08-04, because the size is misleading:

| | Lines | Share |
| --- | --- | --- |
| Generated by Qt Designer and the resource compiler (`ui_*.py`, `rc_*.py`) | 55 876 | **74.5%** |
| Written by hand | 19 116 | 25.5% |
| **Total** | **74 992** | |

Of the generated half, **21 918 lines are a byte-identical duplicate**: `rc_icons.py` exists in
both `pastrocore/gui/` and `pastrocore/gui/icons/`. Deleting one removes 29% of the repository
and changes nothing.

So the surface that actually needs attention is about **19 000 lines**, not 75 000. The
hand-written weight sits in three places: `schedule_calculator.py` (2 812),
`schedule_visualizer.py` (1 817) and `pastrocore.py` (1 208); everything else is under 700.

The `.ui` sources are present in `pastrocore/gui_pyside/`, so the generated files are
regenerable rather than being the only copy. That matters for the styling work.

### What is already in good shape

Worth saying, because it decides where not to spend effort:

- **No bare `except:`**, no `TODO`, no `print()` in the core.
- **Matplotlib figures are closed**: 66 `close`/`clear` calls against 2 figure creations.
- **Qt lifetimes are handled**: 28 `deleteLater`, 14 `closeEvent`. No obvious leak pattern.
- The handler layer already moved onto `Super._apply_methods` in MSB 0.4.0.

## Stage 0 -- a safety net

**Nothing else starts until this is done.** There is currently no test of any kind, so "the
calculations still work" is an opinion. Every stage after this one changes code that produces
numbers, and there is no way to know whether it changed the numbers.

| # | Item | Exit criterion |
| --- | --- | --- |
| S1 | Characterization tests | **Done.** The reference needed no separate file: the fixture project holds eleven results the author computed, and recomputing has to reproduce them |
| S1a | Make the fixture produce data | **Done, by replacing the fixture.** A hand-built observation returned empty frames for eleven of twelve calculations -- most likely a source never above the horizon for those telescopes on that date. A real saved project (ALMA and APEX on 1228+126 over a day) produces rows for all eleven |
| S2 | A round trip of a real saved project | **Done.** Eight tests covering the model, the JSON, the calculated results and each collection separately |
| S3 | A smoke test over the GUI | **Done.** All 53 GUI modules import under the offscreen Qt platform. The main window itself is not reachable: `pastrocore.py` at the repository root shares its name with the `pastrocore` package, so `import pastrocore` finds the package and never the script. Recorded rather than fixed -- renaming the entry point is a stage 1 item |
| S4 | CI running all of it | **Done.** Runs on push and on every pull request, with Qt offscreen |

Characterization rather than unit tests: the point is not that the physics is right -- it is
that it does not *change*. Correctness is established by the author and by the science; this
suite defends it against refactoring.

## Stage 1 -- hygiene

Cheap, safe, and each one measured rather than assumed.

| # | Item | Evidence | Exit criterion |
| --- | --- | --- | --- |
| H0 | Rename the entry script so it does not shadow the package | `pastrocore.py` at the root and the `pastrocore` package cannot both be imported; the script is unreachable, which is why the main window has no smoke test | `import pastrocore` is unambiguous, and the main window is covered |
| H1 | Delete the duplicated `rc_icons.py` | 21 918 identical lines in two places | One copy, imports unchanged |
| H2 | Declare the dependencies that are used but missing | `polars` and `erfa` are imported and absent from `requirements.txt`; `pyarrow` is used through Polars | A clean environment installs and runs from `requirements.txt` alone |
| H3 | Lazy logging throughout | **Done, and the justification was wrong.** Per call the difference is real -- 1 277 ns against 225 with the level disabled, 5.7x -- but a cold `uv_coverage` executes about 680 log statements, so the saving is 0.7 ms in 300: **303 ms before, 312 after, which is noise.** Kept as the convention MSB documents, and because the cost is unbounded in a loop, not as a performance fix | 1 169 calls rewritten through the AST, 16 left where a format spec would render differently. Every one of 682 rendered messages verified identical. A ratchet test holds the line |
| H4 | Review the 222 `except Exception` handlers | A broad catch hides the failure that matters, and MSB 1.0 now offers precise types to catch instead | Each either narrows to an `msb_arch` type or says in a comment why it must stay broad |

## Stage 2 -- the calculations

**A correction, kept visible because the wrong version of it was written first.** An earlier
draft of this page claimed twelve results cost ninety-six evaluations, an eightfold redundancy.
That came from tracing the call graph statically, and it was wrong: the handlers do call one
another, but every one of them goes through `_process_object`, which returns a stored result
instead of recomputing it. Measured on the real test project, one `baseline_projections`
request:

| | Time |
| --- | --- |
| results cached, `time_step` matching | **0.4 ms** |
| cache cleared | **292.3 ms** |
| results cached, `time_step` omitted | 49.1 ms |

The memoisation is real and worth **730x**. Reading a call graph is not measuring, and this is
the second time in two projects that the obvious reading of the code was wrong about where the
cost was.

What the numbers do show is worth acting on.

| # | Item | Evidence | Exit criterion |
| --- | --- | --- | --- |
| C1 | **A call that omits `time_step` silently recomputes everything.** The cache is keyed partly on it, so `calculate(obs, method=...)` without the argument misses every entry and costs 49 ms where a matching call costs 0.4 | 0.4 ms against 49.1 ms on the same cached project | Either the stored `time_step` is the default when none is given, or the miss is reported rather than silent |
| C2 | Profile a cold calculation | 292 ms for **one** observation with two telescopes and a single ten-minute scan. That is the number a real project multiplies | A measured list of what dominates it, with numbers |
| C3 | Act on C2 -- vectorisation, better use of Polars, fewer round trips through Python objects | | Each finding fixed, or recorded as not worth fixing |
| C4 | The same pass over `schedule_visualizer.py` | Not yet measured | Whatever it recomputes per redraw is measured first, then fixed if it matters |

C2 before C3, and both after stage 0, for the reason this section had to be rewritten:
the cost is not where reading the code suggests.

## Stage 3 -- adopt MSB 1.0.0

The framework gained in one day most of what this application had written by hand. This stage
is mostly deletion.

| # | Item | Why it is now possible | Exit criterion |
| --- | --- | --- | --- |
| M1 | Delete the hand-written `from_dict` overrides | Nine of them exist. MSB 1.0 serializes entities inside lists and dicts, restores declared types from annotations, and reads data carrying no `type` field | Only overrides carrying real domain logic remain, and the round trip test still passes |
| M0 | Retire `BaseEntityN`, or find out what MSB must accept for it to go | 98 lines overriding `_validate_type` to admit numpy arrays. Five base classes use it, and each is therefore cut off from everything MSB 1.0 gained: the compiled validator, the exception taxonomy, constraints on annotations. It also raises a bare `TypeError`, contains a duplicated `if value is None: return`, and re-implements the `'value'` special case MSB fixed as F2 in 0.2.0 | Either the override is gone, or MSB has an issue naming exactly what it refuses and why |
| M2 | Move value checks onto annotations | `Annotated[float, Positive()]` is enforced on construction, on `set` and on restore -- where today each class checks in its own `__init__`, if it checks at all | Constraints are declared once, not re-implemented per entry point |
| M3 | Replace the bespoke `Inspector` and `Configurator` with the built-ins | Measured earlier: 20 of 21 handlers held no domain logic. `_configure_scheduleproject` is the one that does | Only handlers with domain logic remain |
| M4 | Catch `msb_arch` exception types | The taxonomy exists, and every type still derives from the built-in it replaced, so this can be done gradually | Error handling names what it means |
| M5 | Version the project schema | `SCHEMA_VERSION` plus `migrate` means a project file written today stays readable when the model changes | Loading an older project either works or fails naming the version |
| M6 | An asynchronous surface for long calculations | `await manipulator.acalculate(...)` moves the work off the loop, so the interface stops freezing without a hand-rolled thread | The interface stays responsive during a full schedule calculation |
| M7 | A request journal for the calculation log | Already shipped in MSB; an audit trail and replay for nothing | A session can be replayed against a fresh project |

## Stage 4 -- storage

The fundamental question, and the reason it is a stage of its own.

**Today:** every calculation lives in memory, and saving writes each result as a Polars
DataFrame through parquet, then base64, into a string inside the project JSON. The consequences,
in order of how much they hurt:

1. **The whole project must be read to open anything.** There is no way to load one
   observation, or the model without its results.
2. **Base64 inflates the parquet by a third**, on top of holding both the encoded string and
   the decoded frame in memory during a load.
3. **Nothing can be inspected without the application.** A project file is a JSON envelope
   around opaque blobs.
4. **Memory grows with every calculation** and is released only when the project is closed.

| # | Item | Exit criterion |
| --- | --- | --- |
| D1 | Decide the shape: most likely a project *directory*, with the model in JSON and each result in its own parquet beside it | Written down with the reasoning, before any code |
| D2 | Load results on demand rather than at open | Opening a project with a hundred calculated observations does not read them |
| D3 | Migration from the current single-file format | Every existing project file opens and is converted, and the old format keeps loading for at least one release |
| D4 | An explicit memory ceiling: results evictable when not in view | Calculating a hundred observations does not grow memory without bound |

The measurements that would settle D1 have not been taken: how large a real project file is,
what share of it is base64, and how long a load spends decoding. **Take them before deciding.**

## Order, and why

| Stage | Why here |
| --- | --- |
| **0. Safety net** | Every later stage edits code that produces numbers. Without this, "nothing broke" cannot be said honestly |
| **1. Hygiene** | Cheap, isolated, and it makes the diff of every later stage readable |
| **2. Calculations** | The largest measured win, self-contained, and safe the moment stage 0 exists |
| **3. Adopt MSB** | Mostly deletion, and it shrinks what stages 4 and 5 have to work on |
| **4. Storage** | Changes the file format, so it wants the test suite mature and the model already simplified |
| **5. Interface** | Last, because the model underneath it has stopped moving by then |

## Not in scope

| Item | Why not |
| --- | --- |
| Rewriting the physics | It is correct. This plan defends it; it does not touch it. Stage 2 changes how often a formula runs, never what it computes |
| Generating the GUI from the model | That is MSB's P4, and it needs persistence first |
| Replacing Qt | No |
| Porting the calculations to a faster library | Not until stage 0 can prove a port produced identical numbers |
